## 系统设置优先，代码只补充

用户确认只增强 Odoo，不接管原生规则。原生规则与存储类别先决定候选库位，补充代码只能删除候选或在同一原生优先级内排序，不能添加库位、扩大范围、写库存或修改系统设置。

系统先保留原生产品／产品类别／包装类型匹配、规则顺序、固定目的地、最后使用位置，以及“最近位置”规则指定的库区和存储类别。多产品托盘必须同时符合每个产品的原生规则范围。原生规则优先级先于代码分数；额外条件排除了高优先级位置时，才使用仍然符合系统规则的后备候选。没有匹配原生规则时沿用默认目的地，不能任意搜索其他库位。

存储类别继续检查包装类型容量、产品容量、全部内容的产品重量及允许新产品的条件。冻结／禁止入库仍由 `blue_stock_rules` 执行。现有原生规则和存储类别记录不会被改写。系统设置在实际分配和完成前重新检查，单据固定的只是补充代码版本。

## 你的示例如何设置

1. 在“存储类别”里，把实际托盘的包装类型容量设置为 **10**。
2. “允许新产品”设置为 **允许混合产品**。
3. 相关商品启用库存追踪和批次追踪, 录入批次号. 将存储类别关联到实际库位，并配置原生上架规则。要在某库区多个位置中查找，原生规则须允许这些位置，例如选择“最近位置”及对应存储类别。
4. 库存 > 配置 > 上架策略，选择公司、仓库、作业类型、增强规则适用库区。
5. 标准示例选择 **同批次号限制（跨产品托盘）**，载入、试算、验证、发布。

空库位可以接收一个明确批次的托盘；非空库位的所有正库存和待上架内容必须与本托盘批次号完全相同。同一个批次号可以属于不同产品，不比较产品专属的批次 ID；比较批次号文本，区分大小写，不自动去除空格或转换名称。已有其他批次、未知批次或本托盘混有多个批次号时拒绝对应分配。

补充代码只有下面这一段，容量和混放检查不写在代码里:

```python
result = []
for candidate in candidates:
    if request["has_single_batch_name"] and (candidate["empty"] or candidate["batch_name_matches"]):
        score = 0 if candidate["batch_name_matches"] else 10
        reason = "同批次号，允许不同产品" if candidate["batch_name_matches"] else "空库位，建立本批次"
        result.append({"location_id": candidate["location_id"], "score": score, "reason": reason})
```

这段代码可人工或后续 AI 编辑，仍走草稿、试算、验证、发布、回滚。新示例采用 `putaway_policy/2`；纯数据解释器兼容 `/1`。AI 聊天和腾讯 API 本轮未连接，记忆适配继续并入拟开发的 `blue_ai_client`。

## 托盘如何计数与移动

实际托盘是 Odoo 的 `stock.package` 记录，并配置包装类型。“托盘”这个计量单位不能代替实际托盘身份。

- 同一外层托盘里有多种产品、多条库存记录或多个内箱，托盘容量只计一次。
- 包装类型容量计入已有正库存托盘与其他未完成作业的待上架托盘，去重后计算。9 个在库加 1 个待上架就是 10，第 11 个不再分配。
- 同一个托盘已经占用／预留了当前位置，不再次增加一个托盘位；它在其他作业中的既有目的地必须一致。
- 整托盘作为一个分配单元，所有有效内容明细共同选位，不自动拆托。散件仍可以按产品容量和单位精度拆分。
- 取消作业释放其待上架占用；在实物完成前重新检查，位置已满或冻结时重新选择合规位置，全部不满足则停止并回滚事务。
- 原生允许创建批次时，可以录入批次名称，由原生完成流程创建不同产品各自的批次记录；不自行放宽原生“允许创建批次”的设置。
- 整托盘内所有商品必须启用库存追踪, 避免无法记账的内容导致托盘计数丢失.
- 空托盘存储不属于本轮，仍在迁移候选清单 5。统计对象为有正库存或有效待上架明细的托盘。

分配使用仓库级事务计数器强制并发事务串行化。仅使用行锁不足以处理 PostgreSQL 的重复读快照，因此计数器写入触发 Odoo 正常重试，重试后重新读取容量。它不改变仓库业务设置，普通用户不能编辑计数器。

## 界面、版本与恢复

真实明细试算会自动包含该托盘的全部有效明细，先显示系统准入数量和补充过滤后的数量，再显示库位名称、分配后托盘数及原因。准确输入／输出在“技术数据”页，可用于开发诊断。试算不修改库存、目的地或单据版本。

作业单“上架策略”页显示整托盘／散件单位、包裹和分配事件。审计记录是分配事件，不能把历史事件行数累计当成物理托盘数量。

旧接管模式的发布快照不能静默用于新增强方式，需要重新验证并发布。开发库升级前没有已发布场景或固定策略的未完成单据，因此无需转换用户代码。模板、菜单已安装，未自动绑定或启用任何仓库策略。
