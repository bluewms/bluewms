# BlueWMS20 开发规则

更新：2026-10-26。当前范围和后续顺序见[开发计划](bluewms20-development-plan.md)，模块职责见[模块架构](../module-architecture.md)。

## 先复用，再扩展

先阅读已有模块、正式合同、测试及当前配置。基础能力放标准模块，客户差异通过独立模块继承；不复制整套 Odoo 模块或直接改官方源码。新增结构、字段、组件和依赖通过正式模块交付，不能由知识文稿或运行时策略临时创建。

所有 addon 直接位于仓库一级目录。自研采用小写 `blue_<领域>_<功能>`；库存 `blue_stock_*`、设备 `blue_wcs_*`、条码 `blue_barcode_*` 分开。第三方保留原名、作者、原许可和来源；改名不改变版权。客户模块采用 `blue_project_<项目>_<功能>`，不把客户 ERP 或设备协议耦入通用库存基础。

## 以实际 Docker 环境为准

本仓库挂载到 Odoo 容器 `/mnt/extra-addons`，相邻 `odoo20` 仅供源码查阅。容器运行版本、依赖和镜像按[部署锁](../../docker/deployment-lock.json)核对，不能把下载源码的版本当成容器版本。

私有配置通过 `BLUEWMS_RUNTIME_DIR` 指定；数据库、附件、API Key 和备份不提交。新增模块使用继承，声明直接依赖，保留 ORM／公司权限和原流程的返回值；前端使用当前镜像自带的 Owl/API。

## 五类业务边界

| 入口 | 当前边界 |
|---|---|
| 上架 | 只在原生规则已准入的候选内进一步过滤／排序，保留容量、托盘和原生优先级 |
| WCS | /4 的 lines/tasks 纯数据合同；人工设备授权、货物覆盖、幂等和库存一次记账由固定模块复核 |
| ERP | /1 单据映射、部分完成事件与盘点差异；连接、权限、幂等、原生库存及持久发送由固定模块负责，新增知识需独立发布 |
| 设备 | /1 类别级 HTTP 报文、响应及完成回调；连接、密钥、状态机和受控位置回写由固定服务执行 |
| 条码 | /1 已有 parse/decide 纯数据合同;固定服务执行计数、选择与获准后续动作,不开放任意 JavaScript/ORM;安装及云端批准状态见条码指南和发布记录 |

AI 会话绑定用户、公司、hook、合同、资产摘要及正式基础版本。业务 Task 必须验证真实身份并显式传给代理，不能回落到日常任务。只使用原生 Wiki 搜索／读页和专用草稿工具；不要恢复固定 Skill 正文、本地通用示例兜底或任意 ORM／shell 工具。

同一项目团队只维护五个业务 Task 和一个日常任务，所有用户共用。用户保留各自 Key／Agent，新增用户只关联既有六个 Task；不得按用户复制任务，运行时不得自动创建 Task。校验团队、运行状态及 Agent 有效关联，不把 Task 创建者等于调用用户作为使用条件。

## 验证与交付

涉及业务逻辑、权限、数量或发布的修改，在隔离 `*_test` 库运行对应回归；测试 dbfilter 必须匹配隔离库。主库不运行测试库存和设备夹具。解释器试算、模块回归、真实模型调用、真实设备验收分别记录，不能互相替代。

新增字段／数据／迁移需要模块升级；先备份数据库与 filestore，并核对客户草稿、版本、发布、人工参数及库存／任务指纹。普通源码拉取或重启不代表已经完成数据库升级。备份应实际检查可读及内容，不把文件存在当作恢复演练完成。

修改通过任务分支和 PR，`main` 使用启用中的保护规则与 squash 合并，不直推或强推。提交说明具体行为、验证范围及仍未验证的边界；不因参考案例通过就声称新生成代码已经验证。操作步骤见[Git 协作](../git-sync.md)。

## 文档维护

开发与运维资料留在本目录体系；AI 知识仅维护 `docs/wiki/`。修改知识后通过[独立发布流程](../operations/knowledge-publication.md)更新云端，Git 合并不会自动发布。历史过程从 Git 查阅，不再整库复制一份到 archive 或离线 Skill 包。

云端配套服务源码和部署材料统一维护在 `docs/cloud/`，不放仓库根目录。正式 Odoo 发行包排除整个 `docs/`；开发仓库继续跟踪文档与云端源码。使用 `git archive` 生成发行包时由根目录 `.gitattributes` 执行排除；其他打包方式同样遵守此规则，并保留各模块的许可及来源声明。
