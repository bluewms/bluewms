# 上架增强策略使用说明

更新：2026-10-18。`blue_stock_putaway` 提供原生上架规则之后的增强，合同／资产模块负责纯数据执行、草稿验证和发布；`blue_ai_client` 通过原生 Wiki 帮助生成代码。

## 从哪里进入

1. **库存 → 配置 → 上架策略**：新建场景，选择“上架增强接口 v2”。已有场景保留原合同及历史，不自动转版。
2. 人工编辑代码和本次测试，或点击 **AI 生成／修改**。AI 从云端读取规范和案例，保存并验证草稿后由用户审阅发布；没有本地“载入通用示例”兜底。
3. **库存 → 配置 → 上架规则**：在原生规则的 **增强策略** 字段选择已发布场景。当前增强版本列可选显示。
4. 选择原生规则和作业明细做真实单据试算，确认托盘、数量、批次和位置后再用于业务。试算不改变库存、目的地或已固定版本。

AI 沟通在当前表单打开加大的浮窗，保留原页面和地址，支持放大／恢复。独立知识讨论入口为 **MuK AI → 宝蓝业务知识 → 上架策略**，该入口没有资产写入工具；修改代码仍从资产页打开。

## 系统设置优先

原生规则决定到达位置、产品／类别、包装类型、目标位置、适用范围及优先级。增强场景不再重复设置仓库、作业类型和适用库区；同公司可复用场景，不能跨公司选择。

系统先检查容量、重量、产品混放、冻结／禁止入库及公司权限，再把准入候选交给代码进一步过滤／排序。实际分配先比较原生优先级，再比较补充分数和位置 ID；分数小也不能越过原生优先级。

例如库位允许 **10 个托盘、混合产品**，AI 只增加“同批次号”条件：第 11 托盘仍不可进入，混放开关仍由系统控制。跨产品比较批次号文本，不比较产品专属 lot ID。

## 托盘与规则边界

- 按最外层物理包裹／托盘计数，内箱去重；已上架与待上架占用均计入容量。
- 整托盘不拆分；仅散件在系统允许时按容量拆分。托盘中各产品须符合原生规则路径，涉及多个增强条件时须全部满足。
- “同单尽量集中”是对合规位置的偏好，不承诺全单全局最优，也不独占库位。
- 严格同批次号策略可以排除其他批次，但仅约束绑定它的原生规则。增强返回空结果后，原生流程可能继续尝试其他规则；未绑定的回退规则不会自动继承限制。全流程必须同批次时，需要检查并绑定全部相关路径。

规范、字段和准确代码只维护在[上架 Wiki](../wiki/domains/putaway/specification.md)与[三个案例](../wiki/domains/putaway/examples/README.md)，不在使用说明中再复制一套。

## 资产、发布与恢复

合同只接受纯 JSON 与受限语法，不提供 ORM、导入、网络、文件或任意 Python。试算使用 `expected_order`，完整语法与限制以本机 `contract_schema` 为准。参考案例通过不能代替新草稿验证。

保存、验证、发布分开；没有正式版本时不执行草稿。首次参与分配时按“作业单＋原生规则”固定正式策略或无增强选择。之后发布、回滚或改绑只影响后续未固定业务，不追溯改变旧单据；回滚也不撤销已经发生的库存移动。

已有代码、测试、不可变版本、发布与执行记录保留在本地。旧代码会话从资产页重新打开后使用原生 Wiki 和“上架策略”Task。身份、公司、合同、草稿或正式基础版本变化时拒绝覆盖。完整工具及来源复核见[原生 Wiki 接入](native-wiki-runtime-20.md)。
