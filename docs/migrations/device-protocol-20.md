# 设备协议 AI 接入与位置回写

更新：2026-10-19。模块：`blue_wcs_protocol` 20.0.1.1.0；配套 `blue_wcs_base` 20.0.1.4.0、`blue_wcs_extension` 20.0.1.5.0、`blue_ai_client` 20.0.1.5.0。实际部署及测试以同名 validation.json 为准。

## 使用入口

WCS → 设备类别，人工新增类别，自动采用统一 HTTP／JSON。公司、负责人、IP、任务路径、Key／Secret、回调凭据继续人工维护，所属设备统一使用类别连接。类别页移除直接新增设备的明细，也不显示查看设备和数量；设备从设备页面添加并选择类别。

类别保存后创建空的协议资产，提供 AI 生成／修改浮窗、与上架／WCS 相同的六个页签：需求、可编辑代码、试算、代码版本、发布历史、审计记录，以及验证、发布、新建草稿、回滚及历史。三个阶段采用独立 `device_protocol/1`，与 WCS 创建 /4 分开；AI 只能保存、验证草稿，不能发布或改人工连接。

## TUSK 与其他接口

人工填写 TUSK 的 `/rpc/createTask`，下发报文为 taskId／targets／configId，HTTP 200 且 msg=success 确认接受。用户确认最终完成回调 taskId／deviceId／targetPoint 保留旧 `/api/blue_wcs_tusk/feedbackTask` 路径、不要求新增 Token，无需在类别额外启用。已有 HIK／WES 回调认证不变。

通用类别还可使用 `/blue_wcs/v1/categories/<类别编号>/callback`，系统从 JSON 值中查找唯一真实任务号，再由固定代码解析并核对；不再手工设置任务号字段。回调凭据空则不要求认证，填写则必须 Bearer。首期仅单条 JSON 最终完成回调；旧 M4、Mita、Modula 资料按厂家分开存入设备 Wiki 参考目录，批量关联／应答、关闭、取消、解绑、盘点等未因此自动实现。

## 位置回写

- 包裹子位置：AI 解析细点，固定程序只写当前任务关联的包裹／载具。配置了容量位置时须唯一匹配空闲位置，包含设备完成但库存尚未入账的占用。
- 实际库存库位：由已发布代码输出 destination_code；固定程序按同公司、当前作业类型所属仓库、条码／AGV 编码唯一匹配既有内部库位，检查原生容量、托盘、重量、混放及冻结后，同步 WCS 实际目的位置与对应库存明细。
- 原计划位置、实际位置、原始回调及协议版本同时保留。部分数量、多计划共用库存行、中间接力、未知／重复库位、越界和原生约束不满足时待核对；改落点后仍有后续固定设备程序时，也先核对路线而不自动改派。不自动新建库位或改已完成库存历史。
- 位置写回与事件确认在同一事务内。重复完成回报不重复记账，库存验证后仍保留已批准子位置。错误回调不确认完成，也不盲目重新下发。

## 发布与运行

每张任务在创建时固定协议版本和报文输入；类别发布新代码只影响后续任务。在途任务禁止更换类别连接、设备绑定、关键连接配置。已发送任务必须经过该固定协议解析，不能用普通设备回执绕过。

真实发送仍使用现有持久队列：先落库声明发送，再进行 HTTP，再记录结果。超时／中断保持待核对。报文试算只计算 JSON，不连接设备；正式发布的转换代码在本地执行，不逐次请求模型。

## 安装与跨机器升级

先备份数据库与 filestore，并核对库存、草稿、发布、类别连接及在途任务。已安装模块按实际清单升级，新协议模块需显式安装：

```sh
docker compose -f docker/compose.yaml stop odoo
docker compose -f docker/compose.yaml -f docker/compose.test.yaml run --rm --no-deps odoo odoo -c /etc/odoo/odoo.conf -d 本机数据库名 -u blue_ai_client,blue_wcs_base,blue_wcs_extension -i blue_wcs_protocol --stop-after-init --no-http --max-cron-threads=0
docker compose -f docker/compose.yaml up -d odoo
```

上述 -u 仅保留本机已安装模块；新库或未启用 WCS 创建扩展的实例按依赖安装，不自动导入旧 19 数据或建立真实厂家类别。各开发机仍用自己的数据库、Key、Agent 和连接配置。

云端共用原有设备 Task 与设备 Wiki，不创建额外 Task 或 Skill。设备合同与批准规范可用后才开放生成，Git 合并不自动部署网关／发布 Wiki。资料维护见[发布流程](../architecture/ai-generation-knowledge-maintenance.md)，准确生成资料见[设备规范](../wiki/domains/equipment/specification.md)。

本轮不向真实设备发送任务。报文、模型及模拟发送验证与真实设备现场验收分别记录。

## 2026-10-19 统一页面与接口设置

移除接口方式下拉、类别设备查看／数量、重复认证与回写设置。新类别直接使用 HTTP／JSON，任务路径不再预填 HIK 地址。厂家说明、版本和案例在设备 Wiki 维护；未明确版本只按唯一版本 1，不自动推断其他版本。

仅保留一处连接参数。Token 空不附加默认认证，有值默认 Bearer；代码可选 headers 用 $app_key／$app_secret 引用类别凭据，引用值为空时省略该头，不把密钥交给 AI。动态签名／Token 交换需要补通用能力，当前不宣称支持。回调凭据填写即校验 Bearer，不再另设开关。

统一模式由代码输出 subposition、destination_code 决定位置处理。目的库位在当前公司、作业仓库内唯一匹配，容量、托盘、冻结、混放、数量和库存一次记账校验保留。旧发布及任务快照不重写，仍保留历史批准范围；重发新版代码后新任务采用统一模式。旧内置适配器仅用于历史运行兼容，不出现在新类别选择中。

更新已安装实例只需备份后升级 blue_wcs_protocol；已有草稿、版本、连接及 Task 不自动重建。新的 Wiki 页以本地 contract_schema 为准，可选 headers 需 schema_version=2。发布 Wiki 后应重开旧 AI 会话以取得新知识版本。
