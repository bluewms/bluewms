# 知识维护与云端发布

更新: 2026-10-26。唯一内容来源为 `docs/wiki/`。本文件是维护流程，不上传到生成知识库。

## 内容与状态

通用规则在 basics；五类规范在 domains 下；每个准确案例只维护一份完整代码、输入和预期。工程部署、Git、私有服务地址、凭据与开发流水不放进 Wiki。合同附件必须与当前实现的 schema 一致，不能由模型摘要替代。

`planned` 仅讨论需求；`draft` 尚未验证；`verified` 表示同版本解释器试算通过；`deprecated` 不供新生成。Wiki ready、平台批准、代码草稿验证与客户策略发布是独立状态。

## 准备与校验

1. 从实际合同和固定业务能力核对规范，不发明字段、方法、认证算法或操作权限。
2. 案例使用稳定知识 ID，写明合同、范围、前提、失败/回退与准确预期；新草稿必须另做本次测试。
3. 运行 `scripts/validate_ai_wiki.py` 校验案例、合同附件及链接。Odoo shell 模式仅允许 `*_test` 库；离线模式只验证纯数据解释器，不替代 ORM/设备/真实模型验收。
4. 整理来源提交、文件与正文摘要，提交任务分支。实际发布清单绑定准确提交，不用未提交工作树伪造版本。

## 发布与读回

1. 从现有私有配置取得六库及团队身份，不新增平行知识库。先备份 Knowledge、Metadata 数据库、Wiki 目录和将变更的服务文件，检查备份内容。
2. 用标准 page/write 逐页写入准确正文及元数据，锁定代码/测试页；JSON 合同包装成完整核对附件。
3. 用 raw/write 保存准确来源快照，再用标准 ingest 建索引。不得让 LLM 重写准确代码或直接改数据库伪造 ready/版本。
4. 等待 ready，通过标准 tools/list、search、read_page 逐页核对正文与摘要。通过后才更新用途、合同、批准页白名单及平台资产版本；候选参考仍明确标识限制。
5. 核对原有 Agent/ACL 和六个 Task 保持正确，用真实业务身份测试各领域检索/完整读页及网关合同路由。真实模型验收需实际调用工具，不预先塞入正文。
6. 保存脱敏发布清单、版本、摘要、回执和验证范围到 [发布记录](../wiki-publication/README.md)。实例 ID、凭据、备份及原始记录只留私有目录。

## 更新和恢复

Git 提交/合并不会自动上传云端。正文或批准版本变化后旧会话应重开；Wiki 没有已验证的历史版本全文读取参数。恢复依靠准确来源提交、发布包和已检查的备份，不从聊天摘要重建。

只整理工程文档时不虚增 Wiki 版本；内容发生变化的库才按流程更新。上传知识不自动发布任何客户业务代码。
