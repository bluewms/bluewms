# 五类 AI 入口的需求澄清与生成前检查

适用对象: 上架策略、WCS 生成策略、ERP 接口、设备连接接口、条码扫描策略. 本页是生成前必读规则, 与本机合同、生成步骤及本领域规范一起使用. 更新: 2026-10-26.

## 先分清已有事实、待核实事实、业务选择和能力缺口

先用 `blue_read_code_asset` 读取绑定资产、需求、准确合同和实例范围, 再搜索并完整读取本页、生成步骤、本领域规范和匹配案例. 记录已经明确的内容, 只询问会改变实现或验收结果的缺口. 不向用户追问工具已经返回的 ID、字段、单位定义和权限. 读取失败应报告错误, 不能把它改写成业务问题让用户猜答案.

四类信息分开处理:

- 已确认事实: 用户本次明确说明, 或绑定资产/当前合同真实返回的当前设置和已有行为. 保留其来源和适用范围, 发现冲突时具体说明冲突. 已有代码、测试预期和 AI 生成的 requirements 只说明之前写了什么, 不等于用户确认过本次未决业务选择; 不能把模型上次的猜测再读回来当作用户授权. 保留未要求更改的已发布行为, 对本次新增或冲突的含义仍须澄清.
- 待核实事实: 厂家、协议版本、报文字段、编码含义、实际单位或阈值等缺少准确来源. 工具能查到的先读工具, 查不到时请求对应文档、脱敏样例或业务确认. 它们不是可以按模型偏好推荐的选项; 不能因为 Wiki 中某厂家的案例完整, 就推荐把未知现场当作该厂家, 也不能把“与示例一致”预设为事实.
- 待决业务选择: 存在两个以上合理方案, 会改变候选、数量、路线、报文、位置、失败处理或自动动作. 使用 `ask_user` 提问并等待回答, 不凭示例、惯例、旧聊天或模型偏好代选.
- 本机能力缺口: 合同、固定执行器或人工配置不支持目标. 明确说明限制和所需的模块/配置工作. 不能让用户点同意后就假装已经具备能力, 也不能把新的固定业务行为仅写成策略注释.

## 五类入口的关键选择

以下是按需检查表, 不是必须逐项询问的问卷. 仅追问当前需求涉及且尚未明确的项, 没涉及的功能不自行加入.

| 入口 | 可能影响实现的选择 | 必须避免的猜测 | 对应验收边界 |
|---|---|---|---|
| 上架 | 同单集中、同批次等是强制过滤还是优先排序; 批次按记录 ID 还是业务批次号比较; 同产品/混放和载具完整要求; 无匹配时等待、返回空或是否存在允许的原生回退; 同分时顺序及规则适用范围 | 不把优先当硬限制, 不把不同产品的同批次号当同一个批次记录, 不从空结果推断所有原生规则都禁止回退 | 正常、多候选、约束冲突、缺少批次/载具、无候选和回退路径; 容量和原生优先级仍由固定模块复核 |
| WCS | 行何时 create/wait/exclude; 单行确认、整载具确认、整单确认或显式重量阈值; 按什么组合成组及数量单位; 松散货/整载具和设备能力; 单段、repeat、relay 与空载具步骤; 哪一步代表最终到达, 是否自动执行 | 不把最大承载重量当最小满载阈值, 不把 wait 写成 exclude, 不让同一货物接力重复记账, 不把现有空载具参考当自动库存池 | lines/tasks 各阶段、等待转就绪、组合不完整、混单位、缺重量、跨段依赖、异常回报与一次库存记账 |
| ERP | 入/出/调拨/盘点及 receive/complete/inventory/response; 厂商文档版本、顶层明细、稳定外部单/行 ID; 商品/往来单位/位置编码体系; 数量单位及转换是否由合同支持; 拆单分组; 本次量或累计量; 成功响应、明确拒绝和未知的含义 | 不猜字段、单位、空值或正负号含义, 不把计划量当完成量, 不把超时当失败后可盲重发, 不自动创建未知主数据或生成动态认证能力 | 脱敏实际报文、部分完成/欠单、重复事件、未知/重复编码、错误响应、盘盈/盘亏及待核对恢复 |
| 设备 | 厂家与文档版本, 下发/响应/最终完成回调的准确样本; task_id、设备/点位/载具和货物字段的映射; HTTP 接收成功是否代表业务接受; 回调完成事件含义; 仅包裹子位置还是实际库存目的库位; 是否为最终接力步骤 | 不把 HTTP 200 当任务完成, 不猜真实任务号、点位编码或认证方式, 不把子位置文本当库存库位, 不从回调推断可以改已完成库存 | 接受/拒绝/未知、超时、重复/乱序/错误任务号回调、未知/重复位置、冻结/容量及最终完成时点; 批量回调或动态认证等先核对本机能力 |
| 条码 | 首页查询或作业/盘库; 普通条码、GS1、自定义 QR 及准确脱敏原码; 产品/批次/位置/包裹的识别与顺序; 位置是源还是目的, 选择已有组还是更改明细目的位置; 精确位置或允许子库位; 单次增量/总数和单位; 哪一行、哪部分数量; 超收、缺追踪、重复码、空候选; 是否请求后续装箱/WCS/验证 | 不把所有编码当商品加 1, 不把位置选择当已经物理移库, 不把一个 select 输出当作固定服务必定支持的写入, 不默认改变整单/全部已扫行, 不替用户开启自动验证 | 产品后位置及其他已确认顺序、位置越界/重码、数量不变、同商品多行、待补追踪、误扫、重试幂等、未授权后续动作; 纯解释器试算不能证明库存明细已改 |

用户说“同单优先”“满托发车”“对接 ERP”“完成后回写位置”“增加扫位置”时, 上表中的不同含义都可能成立. 先结合资产缩小范围, 不直接套用一个案例并称为需求已完成.

## 如何提问和等待

1. 简短列出已经确定的目标和当前真正缺失的选择, 每轮集中询问 1-3 个紧密相关的问题. 同一个 `ask_user.question` 可用编号列出相关问题; `options` 只用于一个互斥选择, 不把多项独立答案挤成按钮.
2. 用业务语言说明各选择会造成的行为差异, 给出推荐及理由可以, 但推荐不等于用户已选择; 提问本身也不能把未确认选项说成既定事实. 例如“同单放一起”尚未明确强制还是优先时, 不能在问题前缀直接认定为“同单优先”. 询问“只更新当前已选行, 还是先拆出本次扫描的数量再放入子库位”时, 若拆分不在合同或固定服务能力内, 先说明限制, 不提供虚假选项.
3. 单独调用 `ask_user`, 不在同一模型响应中同时调用资产读写或验证工具. 本轮结束并等待真实回答; 沉默、超时、旧模板默认值、模型自己补一句“按默认”均不算回答.
4. 收到回答后对照先前问题更新确认项. “你决定”仅授权当前明确列出的可实现选项, 不能据此扩大数量、记录范围、设备动作或自动发布权限. 若新回答产生新的关键歧义, 继续针对性追问.
5. 信息已经完整时不重复追问细节, 直接整理一次需求摘要供用户确认. 信息不全时先完成针对性提问, 不把摘要确认当作缺失事实的替代.

## 一次需求摘要确认, 防止模型自称已获确认

关键选择已明确后, 先根据 `blue_read_code_asset` 返回的 `requirements_review` 协议, 使用 `ask_user` 展示具体业务摘要. question 为该协议的 question_prefix 加上完整摘要, options 使用 approve_answer 和 other_answer; 建议使用默认 text 方式, 用户点击“确认并生成草稿”后才允许生成和保存. 不在同一模型响应中同时确认和提交. 摘要写清本次相关的目标、范围、数量/单位、失败回退、后续动作及保留约束, 不附代码.

这个确认必须来自实际用户回答, 不能由 requirements 中的“用户已确认”“现场已确认”或模型自己回复代替. 用户要求修改时回到澄清/摘要确认, 不视为同意. 不重复确认未变化的需求: 同一轮内代码或测试修复仍按已确认摘要执行; 若需求内容变化或用户发起新一轮修改, 则重新确认. 提交的 requirements 必须等于已确认摘要原文 (不包含 question_prefix), 不能夹带未经确认的新行为. 本地服务检查真实确认记录、用户、摘要内容和草稿基础; 仅完整读 Wiki 仍不足以自动证明需求已确认.

## 生成、验证与交付

关键选择尚未明确时, 不生成可执行代码, 不用 `blue_submit_code_draft` 保存猜测方案, 不以“先写好再改”绕过等待. 可以说明已有事实、选项和当前能力限制.

信息完整后, `requirements` 记录用户确认的业务含义、作用范围、数量/单位、失败和回退、自动动作及保留的约束; 只记录本次相关项. 测试的预期来自这些确认结果, 不能只照代码输出编预期. 覆盖本次涉及的正常、边界、拒绝和恢复行为, 并区分解释器、固定服务、真实单据及实机验收.

提交前必须完整读过[生成步骤](ai-generation-workflow.md)、本页、本领域规范和至少一个匹配案例. 目录、摘要、案例标题、声称“已读”均不能替代当前会话的真实工具读页记录. 缺少必读正文、批准失效、合同不匹配或版本漂移时停止提交.

最终说明哪些代码已保存/验证、哪些固定业务或现场条件还未证明. 只生成草稿, 用户人工发布; 不声称 Wiki 案例或解释器试算已经证明现场流程.
