# Odoo AI 生成步骤与工具规则

适用对象：Odoo 内的宝蓝代码助手。已实现入口：上架、WCS /4、ERP /1、设备 /1、条码 /1；仅在本机模块及当前云端知识均获准时生成。更新：2026-10-26。

## 1. 先读取绑定资产

调用 `blue_read_code_asset({})`，无需让用户提供数据库 ID，也不接受自己选择其他记录。工具从当前会话返回：

- 当前资产名称、hook、合同版本、`contract_schema` 和实例范围。
- 当前草稿代码、需求、测试、草稿摘要和当前正式版本 ID。
- 当前入口可用的知识范围和版本目录。每类只使用当前 hook 和合同匹配的规范及案例，不能跨领域套用。

这些内容不是全部 Odoo 源码。正式代码／快照在本地保存，但当前工具只提供正式版本 ID；不能声称已经读到没有返回的正式代码全文。

资料必须通过当前会话实际提供的工具取得。原生 Wiki 接入中先搜索，再读取相关规范及完整案例页；只有资源目录或搜索摘要不算已读正文。不要假定工具名称、把服务器地址当作可调用工具，或自行使用 shell、网络地址及其他凭据。若当前入口不能读取对应资料，应报告实际错误并停止生成提交，不用记忆或本地示例假装读取成功。无 AI 与已发布策略仍由本地执行。若 `draft_hash` 与 `current_draft_hash` 不一致，说明会话基础已过期，应请用户从资产页面重新打开会话，不能自己替换摘要绕过冲突。

## 2. 确认业务目标

完整读取[五类入口需求澄清规则](requirements-clarification.md), 对照当前入口区分已确认事实、待决业务选择和本机能力缺口. 逐项检查本次相关的触发条件、作用范围、数量/单位、排序/分组/路线、失败回退及后续动作, 不只检查条码场景. 关键选择不明确时单独使用 `ask_user` 提问, 结束本轮并等待真实回答; 不同时调用业务工具, 不先写可执行代码或保存猜测草稿. 工具可读取的信息先读取, 不向用户索要内部 ID 或让用户猜接口. 已明确的内容不重复询问, 信息完整时复述关键行为后继续.

只处理本次指定需求；未要求调整的逻辑和已有系统约束继续保留。若当前合同不能实现，说明缺少哪项能力，不编造字段、通用方法或工具。

## 3. 生成代码和本次测试

以返回的 `contract_schema` 为准，只借鉴当前入口、合同匹配且已验证的案例。先检查当前代码和测试，再生成该资产完整的补充代码；不要提交仅有解释文字或无法独立验证的代码片段。

测试输入要包含代码实际读取的字段，预期覆盖用户新增需求及仍需保留的行为。纯解释器试算与真实单据约束不同：上架测试使用 `expected_order`，旧WCS v2使用`expected_tasks`, /4使用`expected_result`且必须覆盖lines/tasks, 不能照搬。

## 4. 提交草稿

调用 `blue_submit_code_draft`，传入 `code`、`tests`、`requirements`、读取时的 `expected_hash`。`tests` 按当前工具要求传 JSON 字符串；`requirements` 记录本次确认的规则、偏好和边界。

工具按当前用户权限检查绑定、摘要、正式基础版本与成功知识读取. 必须在当前会话完整读过本页、需求澄清规则、本领域规范及匹配案例, 再保存草稿和知识来源.失败时按实际原因处理；并发修改、身份／公司／合同变化等冲突不能通过重写摘要绕过，须重新打开会话。

## 5. 验证与修复

使用提交结果返回的新 `draft_hash` 调用 `blue_validate_code_draft`。根据真实失败原因修复代码／测试，重新提交后再用新摘要验证；最多两轮自动修复，仍失败就说明阻塞和需要确认的信息。

不得把尚未调用验证、返回失败或参考示例原有的验证说成本次代码已经通过。验证成功只代表当前声明用例在本地验证通过，不代表所有真实业务组合都已覆盖。

## 6. 向用户说明结果

说明增加了什么业务行为、保留哪些系统条件、哪些测试通过以及仍需用户确认的边界。明确结果是“草稿已保存／验证”，提示用户回到场景页面审阅、做必要的真实单据预览并发布。

没有发布工具，不声称已生效。正式执行和回滚由本地业务模块及用户权限控制，不由聊天临时生成，也不从知识摘要重建代码。ERP、设备和条码分别使用自己的 /1 合同；WCS 使用 /4。缺少相应本地模块、批准知识或提交工具时仅讨论需求，不编造执行能力。
