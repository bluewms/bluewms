# Odoo AI 原生 Wiki 检索与五类知识库规划

日期：2026-10-18。适用读者：知识维护者与接入开发者。此文是工程方案，不发布为 Odoo AI 的代码生成教材。

**当前状态：六个 Wiki 已发布 29 份准确资料，索引 ready，逐页读回摘要一致。通用／上架／WCS 已批准；ERP／设备／条码为 candidate，正文明确 planned。Odoo 页面中的正式工具尚未切换到原生 Wiki。** 发布及本地模型检索证据见[本轮验收记录](../wiki-publication/native-wiki-20261018.md)。

## 1. 前次规划基线（正文发布前）

- Git 同步基线：`3b7a801`，已包含 WCS /4 行级决定、多任务编排、完整合同和 AI 草稿流程。上架与 WCS 共用 `blue_ai_client` 的会话保护和浮窗。
- 现场 Hub／Core／Proxy 镜像仍为 1.0.2，三个服务健康；代理知识注入开启。现场 Wiki 注入源码摘要与此前核对版本一致，仍是资源目录和查询工具说明，不是自动完成正文检索。
- 标准 `POST /v3/tools/list` 可发现 Wiki 的 `get_info`、`search`、`read_page` 等只读工具；`POST /v3/tools/call` 执行它们。现场 `search` 明确为 **BM25 全文检索**，不是已验证的向量语义召回。
- 现有 `bluewms-odoo` 为 draft／版本 0，原始上传列表为空。它保持原样，建议后续承担通用生成规则；本轮没有重命名或改正文。
- 五个新业务库均为 draft／版本 0，团队可见，未上传正文、未批准、未绑定 Agent。已用另一团队成员验证可见性；draft 的标准搜索返回空结果，不能用于生成。
- 原 `bluewms-policy-authoring` Skill 仍为批准的版本 4，只有原五个资源，没有 WCS 的 06／07。它保持不变。WCS /4 代码就绪不等于已有可用的批准云端正文。
- 本机 Docker 命令当前无法连接守护进程，本轮只同步源码，没有升级或验证这台机器的新 WCS 数据库；不能套用另一台电脑的部署验收结果。

资源 ID、服务器地址、原始回执和数据库备份保存在私有运维记录。公共方案只记录逻辑名称和职责，避免其他环境照抄实例 ID。

## 2. 一个通用规则库，加五个业务库

| 逻辑范围 | 云端名称 | 资料职责 | 首批合同／状态 |
|---|---|---|---|
| common | 现有 `bluewms-odoo`（建议作为通用库） | AI 生成任务、工具步骤、测试与人工发布规则 | 现有草稿不改，待整理发布 |
| putaway | `Odoo-AI-上架策略` | 原生规则增强、同单／同批次、整托与回退边界、三个案例 | `putaway_policy/1`、`putaway_policy/2`；空白草稿已建 |
| erp | `Odoo-AI-ERP接口` | 字段映射、数据转换、幂等及异常需求案例 | 合同未开放；空白草稿已建 |
| wcs | `Odoo-AI-WCS任务生成` | 全行决定、分组、数量／位置含义、设备程序编排及十个 /4 案例 | 新 AI 生成仅 `wcs_creation/4`；空白草稿已建 |
| equipment | `Odoo-AI-设备接口` | 已注册适配能力内的报文映射、状态解释、动作边界 | 合同未开放；空白草稿已建 |
| barcode | `Odoo-AI-条码策略` | 扫描顺序、解析／校验、确认状态和允许动作 | 合同未开放；空白草稿已建 |

本表记录初建时状态；当前六库的页数、批准及检索验收以[发布记录](../wiki-publication/native-wiki-20261018.md)为准。

保持一个项目团队、每用户自己的 Agent／Key。业务分类继续使用既有五类 Task，不按功能复制团队或人格。物理分库便于维护和限制查询范围，不代替用户／Agent ACL，也不按每次聊天新建库。

通用规则不复制到五个业务库。每个业务库按“入口说明 → 合同适用范围 → 字段业务含义／约束 → 独立案例 → 已知限制／版本记录”组织，一个案例一页。当前实例的完整可执行合同仍由本地实时返回，Wiki 说明不能覆盖它。

以后新增业务入口，增加 hook、运行合同、知识库注册和测试；不改变现有五库的含义。客户特殊知识确有需求时增加受限的客户补充库，仅在客户／公司授权匹配后叠加，不能覆盖系统硬约束。

## 3. 来源与批准

维护来源统一为 `docs/wiki/`，该目录只含供 Odoo 内 AI 生成增强代码使用的规则和案例。服务器配置、Git 流程、源码开发规范和排错历史不上传到这些生成库。

上架采用规范和三个独立案例；WCS 采用 /4 规范、配置语义、合同核对附件与十个独立案例。`docs/knowledge/` 综合旧稿和 /1–/3 旧合同不作为 /4 的生成来源。旧正式策略、历史合同和固定任务仍在本地保留，不因新库改变。

每份发布资料记录稳定知识 ID、hook、适用合同／模块版本、来源提交、准确代码、试算输入／期望、验证证据、作者、批准及内容摘要。代码和测试按源文件核对，不用 LLM 摘要替代原文；长案例拆成独立完整页，不能截断代码或删除失败边界以凑长度。

**索引 ready、资产 approved、页面锁定是不同状态。** ready 只证明索引可检索，锁定只保护编辑；生成还必须满足实际批准记录和合同匹配。不能相信正文自己写着“已批准”就放行。维护者发布清单与平台资产批准状态共同约束可读的发布页集合，候选页不混入生产库。

## 4. 查询范围由绑定资产决定

推荐路由为：

| 已绑定 hook | 默认允许检索 |
|---|---|
| `putaway_policy` | common + putaway |
| `wcs_creation` | common + wcs，且仅 /4 的已批准适用资料 |
| `erp_mapping` | 将来开放后 common + erp |
| `device_protocol` | 将来开放后 common + equipment |
| `barcode_policy` | 将来开放后 common + barcode |

现场知识注入主要按 Agent 固定资产列目录，不能只依赖 Task 名称自动选中对应业务库。路由必须从服务端已绑定会话的 hook、合同、用户／Agent 和公司获取；不让模型自行指定 team、user、任意 Wiki ID、URL 或管理凭据。

按逻辑范围注册的实际 Wiki ID 放在每个部署自己的配置中，不写死在模块源码。查询前校验该业务用户／Agent 对指定 Wiki 的权限，再校验 ready、approved 和适用合同；不能因同一个服务租户内能调用标准接口就认定拥有全部资料权限。

## 5. 推荐接入：标准检索，受限转发

用户体验是 AI 自动查资料，用户无需手动挑页。实现上由模型根据当前需求发起腾讯标准搜索／读页工具，而不是假设每次代理请求已经自动完成全文 RAG。

1. `blue_read_code_asset` 只读取当前本地资产、真实合同和可用知识范围，不再强制拉取固定 Skill 资料包。
2. 增加两个受限只读工具（拟命名）：`blue_search_code_knowledge(query)` 和 `blue_read_code_knowledge(page_ref)`。只允许当前入口范围；页面引用必须来自本会话已授权搜索结果。
3. 由接入层通过 `/tools/list` 发现该版本标准工具，调用 `/tools/call` 的 `search`、`read_page`；权限／ready／版本检查可用 `get_info`。正文检索与索引由腾讯完成，不在 Odoo 重做全文搜索或维护示例副本。
4. 模型先搜索、再读取相关规范和案例完整页，记录来源；没有足够批准资料时明确报告，不猜代码、不跨库兜底。
5. 保持已有 `blue_submit_code_draft`、`blue_validate_code_draft` 及用户发布流程。提交前要求已取得本入口、当前合同匹配的真实知识引用。

当前模型 API 是代理入口，而 Wiki 返回的 service_url 是 Docker 内部地址；**直接把该地址交给本地模型工具不可视为已打通**。实施前需验证现有鉴权通道能否以业务用户身份调用 Wiki。若需要 HTTP 转接，只增加身份校验／固定路由／只读操作转发，不增加第二套检索引擎，不把管理服务 Key 放进 Odoo 用户端或提示词。

MuK 继续主持本地业务工具循环，腾讯负责知识服务。后续若要改成完全云端自动检索注入，需要另设云端知识检索步骤和可核验的来源回传；不是本方案已经完成的功能，也不能同时在两端重复执行草稿写入。

Skill 以后只保留通用生成步骤和工具纪律，不复制五库中的案例正文。现有桥接及 Skill v4 在新方案验收前保持原样，新链路失败不能悄悄回退旧 Skill 或其他领域案例。

## 6. 适配最新 WCS，保留业务保护

- 上架和 WCS 一起改接入层，不能只改上架后让 WCS 仍依赖另一套正文副本。
- WCS 新生成保持 `wcs_creation/4` 门槛，保留完整 `contract_schema` 及当前兼容别名；不把 /2 或 /3 的输出套入 /4。
- 会话仍固定资产、hook、合同、公司、用户身份、草稿摘要和正式基础版本。保留并发拒绝、人工发布、版本固定、回滚和纯数据解释器。
- WCS 的 create/wait/exclude 行决定与任务阶段分开；人工设备／任务类型、数量覆盖、整载具、依赖和库存一次记账仍由本地固定模块复核。
- 不自动转换旧客户草稿、已发布 /1–/3、作业类型绑定、固定计划或设备报文；知识迁移不执行设备任务、不改库存。

旧引用来源为 `tencent_skill_bridge`，新引用拟为 `tencent_wiki`。新会话固定检索方式和已读取页面的 Wiki／页面版本、合同、摘要及批准证据；旧会话的来源类型不能直接伪装成新引用。迁移不重写旧不可变代码版本的知识来源。

平台现场 Wiki 版本以字符串返回，例如草稿为 `"0"`；新引用需明确版本类型和校验，不能照搬旧 Skill 整数版本假设。正文版本漂移、无权限或批准失效时中止或要求重开会话，不静默换资料继续提交。

标准 `read_page` 当前只接收 refs，没有已验证的历史版本读取参数。不能照搬 Skill 的“指定旧版本再次读取”能力。读取前后核对 Wiki 版本并冻结实际正文摘要，同会话再次取页若版本已变则拒绝混入；若平台未返回页修订号，使用真实页引用、整库版本与正文摘要，不伪造页版本。长期追溯还要保留来源提交和批准发布包，不能把 Wiki 版本号当作能恢复任意历史正文的保证。

## 7. 检索质量与大小

当前 BM25 检索需要明确关键词。可由模型按业务意思生成关键词，并带 hook／合同／关键字段，如“同单 same_picking”或“WCS repeat /4”；不能承诺已有向量语义召回。每页标题、稳定 ID、适用合同和中英术语有助于精确召回。

按需读取一到几个完整案例，不把 WCS 十个案例及全部合同全文一次塞进提示词。保留响应／总正文／超时边界；当前 32 KiB 资料包限制是既有兼容实现，不是腾讯知识库容量。新方案应按单页／累计引用预算另行验证，超量时缩小查询或选择较少完整案例，不截断准确代码／测试。

## 8. 实施次序与验收

| 阶段 | 内容 | 当前状态 |
|---|---|---|
| P0 | Git 同步、现场工具核对、五库草稿与团队可见性 | 已完成；旧 Skill 保留 |
| P1 | 确定业务用户到 Wiki 的鉴权通道，增加两只读工具、路由和引用模型 | 隔离验收采用临时 SSH 只读转发；正式 Odoo 工具与 HTTPS 通道尚未接入 |
| P2 | 发布通用规则、上架和 WCS /4，验证准确正文与批准清单 | 已完成；29 份资料逐页读回一致，后三类仅 candidate／planned |
| P3 | 同时切换上架和 WCS，新旧来源明确分开，回归及真实对话验收 | 尚未切换 |
| P4 | 稳定后退役额外 Skill 正文副本，再逐类接 ERP／设备／条码合同 | 后续 |

验收必须覆盖：

- 标准工具发现／搜索／全文读取真实命中；不能把 draft 的 HTTP 200 空结果当检索成功。
- 同一 Agent 切换上架／WCS 时范围正确；模型伪造库 ID／用户／URL、跨公司或无权限均拒绝。
- BM25 中英术语与无结果处理；未批准、未 ready、合同不匹配和来源版本漂移均不能提交生成代码。
- 上架三个案例、WCS 十组代码和试算与对应本地解释器一致；源代码摘要与 Wiki 实际页一致。已有交接的 260 项结果不代替本机新链路重跑。
- 检索引用真实持久保存，提交、验证、人工发布与回滚不回归；网络失败时已有正式业务仍可离线执行。
- 在隔离测试库做生成及业务回归，主库不创建测试搬运任务或测试库存；真实设备另行验收。
